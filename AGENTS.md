# AGENTS.md

Chrome/Edge (Manifest V3) extension: reads the transaction table on a supported bank page (Maybank2u and CIMB Clicks) and adds new rows to BudgetBakers Wallet through its REST API. Built for the owner's own use and friends; others are welcome to use it. Repo: https://github.com/Atsukio/bank-to-wallet-sync (branch `main`).

**Shared rules first:** this file covers only what is specific to this extension. The rules common to all of the owner's extensions (design, permissions, privacy, releases, commit messages, Windows gotchas, working with the owner) are in `../extension-kit/CONVENTIONS.md` (imported by `CLAUDE.md`). Where the two differ, this file wins.

## Working here (read this first)
The steps for every task, whichever model or person does it. The sections after this are reference: read the one for the area you touch.

1. **Understand before editing.** Read the section below for the area, then the code (in `popup.js`, its section comments first). Find every caller before changing a function's shape. Never guess Wallet API fields: read the spec (see Wallet API notes).
2. **Make the smallest change that fits.** Match the surrounding code. No new dependencies, files or abstractions unless asked; don't refactor or reformat code outside the task.
3. **Test as you go.** Run `npm test -- <name>` for the area (`logic`, `scanner`, `background`, `panel`, `pages`, `build`), then the full `npm test` before calling it done. Add or update a test for each behaviour change. If the browser won't launch, set `CHROME_PATH` to Brave (`C:/Program Files/BraveSoftware/Brave-Browser/Application/brave.exe`).
4. **Look at UI changes** in light and dark, with `npm run screenshots` or the `chrome-devtools` MCP (see Testing).
5. **Done means** the tests pass and, in the same change, this file is updated if it describes what changed, and `PRIVACY.md` / `store/LISTING.md` are updated if data handling or permissions changed. Report what you ran and the result, and say plainly what you could not verify.
6. **Stop and ask** before adding a permission or host permission, changing what is stored or sent, renaming or dropping a settings key, editing `../extension-kit`, committing or pushing, or when the request is ambiguous. One short question beats a wrong guess.
7. **Never** use or repeat real bank or Wallet data (Demo data and synthetic fixtures only), open `.env` files, point a browser tool at the real bank sites or Wallet, or hand-edit the generated colour block in `style.css`.

When this file and the code disagree, trust the code and tests, then fix this file.

## How things work

**Reading the page** (`popup.js` `readPage`)
- Auto-read: the panel reads the active supported tab when it opens and re-reads (debounced 100 ms) on a `b2w-page-changed` message, `tabs.onUpdated` for the active tab and `tabs.onActivated`. `watchPage()` (MutationObserver, 250 ms debounce, ping only) is injected on every read because the site changes its table without navigating. Chrome cannot open a side panel without a click, so the panel never opens by itself.
- `auto` reads are gated by the `autoRead` setting and skip when `busy`, in demo mode or without a token; `quiet` reads refresh in place (after an account change, ignore, undo); `force` re-checks Wallet even if the bank rows are unchanged. Switching back to a tab or focusing the panel forces a Wallet check. Manual button reads always run.
- `carryOver` keeps what the user did by hand (ticks, flipped signs, transfer choice, manual category) across re-reads, keyed by `signature` (date|desc|amount as read).
- `collectPages`: rows from earlier pages are merged into the list until **Clear list**.

**Amount signs** (`scanner.js`): a wrong sign adds an expense as income, so it is checked three ways.
1. `parseAmount` reads the cell text (leading/trailing minus incl. Unicode minus, brackets, DR/DB/DEBIT).
2. If the text has no sign, `visualSign` reads the cell's CSS: a minus drawn by `::before`/`::after`, or red/green text. Maybank2u draws debits in red with the minus in CSS, so text alone read them as positive.
3. `reconcileSigns` overrides using the Balance column when there is one (balance movement between neighbouring rows is the truth). Rows it can't verify are flagged `unsure` only if the text proved wrong elsewhere on the page; the panel leaves them unticked with a Flip sign button.

**Which Wallet account** (`popup.js` accounts section)
- `detectAccount()` (best-effort, **never verified on the real page**) returns `{label, digits}` from headings, an account drop-down or account/card-classed elements. `bankKey` = `d:<last4>` else `l:<normalised label>`. `settings.accountMap[key]` maps it to a Wallet account; else the default `settings.accountId`; else the panel asks (`resolveAccount`, Add disabled). Choosing in the picker saves the mapping (or the default if no bank account was detected). The detected label is shown under the picker so it can be checked ("Reading: …", one line: a long name is cut with "…" while the masked last four digits stay visible, the full name is the tooltip, and any full account number in the label is dropped), and **Compare** prints it (digits masked).
- Accounts come from `listAccounts` (active only), cached 10 min and stored as `accountList` for Settings.

**Matching against Wallet** (`matching.js` `matchRecords`)
- Nothing is written to Wallet to track syncs. Existing records for the date range are paired one-to-one, three passes: exact description + same type → done; same type → likely; **opposite type → likely with `typeMismatch`** (shown as "Type differs", no Replace, so a wrongly signed record isn't hidden as "In Wallet"). **Fix in Wallet** (`fixType`, bulk `#fixAll` when 2+) PATCHes only `amount: { value: <bank signed amount> }`, which also sets the type; not offered when the Wallet record is a transfer (`existingRecords` marks `transfer`), since flipping one side breaks the pair. Ignored rows take no part. `sameDescription(walletText, bankDesc)` is directional: it ignores case/punctuation and accepts an 8+ char truncated prefix either way, or a Wallet note that contains the whole bank description (8+ chars) anywhere, because people add details to notes. Records with `recordState: void` are ignored.
- Likely rows show the Wallet note and offer **Merge notes** (`mergedNote`: "<wallet note> · <bank description>", the user's part shortened with "…" to fit 255, never the bank's) and **Replace note** (note = bank description); each button's tooltip shows the resulting note; plus bulk `#mergeAll` / `#replaceAll`. Both PATCH only `note`. When the row has a `payee` (CIMB DuitNow) that differs from the Wallet record's `counterParty` (kept by `existingRecords`), the row also offers **Set payee** (or **Set payer** for money in; PATCH `counterParty` only, the row stays likely) and **Replace all** (note and `counterParty` in one PATCH, the row becomes In Wallet), plus bulk `#payeeAll` and `#bothAll` ("Replace all N"; both act on every eligible row, not only ticked ones, like the other bulk buttons). `sameDescription` also treats any " · " part of a Wallet note equal to the bank description as a match, so merged notes match even when the description is shorter than 8 characters. `existingRecords` keeps the record's own `note` separately from its other texts for this.
- A fourth pass catches records on a nearby date: same amount and type, Wallet dated up to `MAX_DATE_LAG` (3) days before (logged before the bank posted it) or after (an automated/scheduled Wallet record) the bank row; closest day first, the earlier side wins a tie, same description preferred, run last so a real bank row on that other day keeps its record. Sets `t.dateLag` = bank date minus Wallet date (negative when Wallet is later); the row offers **Use bank date** (`moveDate`: PATCH `recordDate` shifted by the lag, so the time of day is kept; bulk `#moveAll`), and Merge/Replace only after that. `analyse` fetches records from `shiftDate(earliest, -MAX_DATE_LAG)` to `shiftDate(latest, +MAX_DATE_LAG)`; `showCoverage` counts only the bank's dates.
- The REST API serves its own synced copy of Wallet, so a record deleted in the app can keep showing for a while. `existingRecords` captures `X-Sync-In-Progress` and `X-Last-Data-Change-At`; the coverage line shows them. **Compare** lists each Wallet record's source, state and updatedAt.

**Categories** (a record with none shows as "Unknown expense")
- Order: remembered manual choice (`categoryMemory`, keyed by `memoryKey`) → Wallet rule (`GET /record-rules`, `matchRule`: substring, longest keyword, skips transfer rules and other accounts' rules) → `guessCategory` from `categoryHistory` (last ~6 months, any account, up to 1000 records; same description, else same merchant; same income/expense type; "Unknown" ignored; most common wins). The per-row **Change** picker is a text box with a `<datalist>` (`#categoryOptions`) that filters as you type (Enter takes an exact name or the only match, Escape closes; a name shared by two groups gets its group in brackets). While it or the transfer picker is open (`picker`), `render` leaves the list alone, because the panel re-reads when it gains focus and the first click into it would wipe the picker; closing it renders, and the choice goes to the row now in `txs` with that signature (`liveRow`). It uses `listCategories` (`GET /categories`, response key assumed to be `categories`, **unverified live**).
- Caches: rules 5 min, history 10 min, categories 30 min, accounts 10 min. Failures never block adding.

**Transfers** (`transferRules` in Settings, or the per-row button, "Transfer to" for money out and "Transfer from" for money in, which also words the row's transfer line): the record is created with `transfer: { pairingMode: 'new', accountId }` (no category/labels); Wallet creates the mirror record, whose id comes back as `createdMirrorRecordId`. The other account's page then sees the mirror as "In Wallet". **Unverified live.**

**Undo**: after an add, `lastAdd = { groups: [[id, mirrorId?]], at, tabId }` is kept **in the panel's memory only** (the owner asked that Undo belong to the page it was added on): shown only on that tab, cleared when the tab reloads or navigates (`tabs.onUpdated` status `loading`; an in-page change like CIMB's keeps it) or closes, when the panel closes, or after 15 min. Older versions saved it in storage; `init` removes that key. Undo calls `DELETE /records` with `{ ids }` (max 10 per request; a transfer and its mirror must go in the same request, hence `chunkGroups`). **Unverified live**; demo mode pretends.

**Balance check** (`readBalance` in `scanner.js`, `renderReconcile` in `popup.js`): reads the page's "Outstanding Balance", else "Current/Ledger", else "Available", else "Statement" (and Malay labels), the amount right after its label, up to 5 levels up (CIMB: `.value-box > label + .value number-cmp`; Maybank2u card: `<p>` label in `.panel-body`, amount in the sibling `.well`). Outstanding beats statement because a card's statement balance is only what was owed on the statement date (the owner asked for this). Compared with the Wallet account's balance; a card/loan (`accountType` CreditCard/Loan/Mortgage, or an "outstanding"/"statement" label) counts the bank figure as owed (negative); on such an account an "Available" figure is the credit left, so the check is hidden. **Adjust** asks first (warning if new rows aren't added yet, since they'd be counted twice), then POSTs one record for the difference: note "Balance adjustment to match the bank's …", `recordState: 'reconciled'`, dated now, no category (the API has no adjustment concept). It goes into `lastAdd`, so Undo removes it. The panel shows two columns with a divider (the owner's layout; `.balances`, a grid whose `.side` columns use subgrid so the rows line up): Wallet (label `#walletLbl`, "Wallet (demo)" in demo mode; `#balance`, the signed balance; `#reconcileText`, "▲ +RM x than bank" / "▼ -RM x than bank", Wallet minus bank as signed balances so on a card owing less is ▲, or "Matches bank ✓") and Bank (`#reconcile`: label, `#bankLine` "<amount>[ owed]", the bank's own label as the column's tooltip, and Adjust). Then `renderWhy` explains a difference from the page, one line each (tooltips say more): "Not in Wallet: N (sum)" for new rows not added yet (the bank counts them), "Not in Bank: N (sum)" for Wallet-only records (the bank doesn't yet) and "Other: RM x (dates not on this page)" for any remainder; bank − Wallet = new rows − Wallet-only + other.

**Wallet-only records** (`walletOnly`, `renderWalletOnly`): `matchRecords` returns the records no bank row claimed; those dated strictly inside the page's dates (its first and last dates can carry on over a page break, so a record there may just be on the other page; when the last row is within `RECENT_DAYS` (7) of today the page counts as current, its last date counts and the range runs to today, as does the Wallet fetch), and not matched by a bank row on another page read in the same tab (`seenInBank`, per tab and account, in memory, cleared when the tab closes; the owner hit this paging through Maybank2u, where page 2 is recent enough to count as current) go into the main list among the bank rows by date (`walletRow`: `li.wallet-only`, no checkbox, read-only, chip `.chip.notbank` "Not in Bank"; a **Delete** text button, not on transfers since the mirror would be left behind, that turns into "Delete from Wallet?" (`.confirm`, error colour) for 5 s and deletes on the second click, `deleteWalletOnly`: `DELETE /records`, then `deletedIds` hides it from later reads because the API's synced copy can keep returning it; demo pretends), and the summary counts them. Usually what the bank hasn't posted yet. Tests' `rows()` skips them; use `li.wallet-only` to check them. `detectAccount` first uses `option[data-account-no]` (CIMB tags its account picker with `data-label` / `data-account-no`).

**What's new** (`whatsnew.js`, `changelog.js`; the shared behaviour is in `CONVENTIONS.md`): the entries are `CHANGELOG` in `changelog.js` (`changesSince`, `compareVersions`). The card shows in the side panel and in the "not supported" popup (the badge is on every tab, and clicking it on a non-bank site opens the popup); both call `showWhatsNew(box)`, which also re-renders on `storage.onChanged`, so a preview from the console shows up with the panel open. The panel's per-tab row-count badge overrides NEW on that tab only. A quiet release (no entry between the old and new version) sets neither `whatsNewFrom` nor the badge in `noteUpdate`, so no NEW appears only to vanish when opened; if the card still finds nothing (e.g. a console preview), it clears both silently. `showWhatsNew(box, log)` takes a changelog for tests.

**Bank access** (`sites.js`): a required host permission added in an update disables the extension for existing users until they accept it, so every bank added after Maybank2u is `optional: true`, with its origin in `optional_host_permissions` (a build test keeps `host_permissions` to Maybank2u and the Wallet API). Without the grant the worker can't see the tab's URL and treats it as unsupported, so the icon opens the "not supported" popup; clicking the icon gives that popup the URL (`activeTab`), and on such a bank it asks "Allow CIMB Clicks?" and calls `chrome.permissions.request` (Chrome may close the popup for its prompt; `permissions.onAdded` in the worker re-syncs the tabs either way, and the user clicks the icon again). The side panel asks the same way if it meets one (when "Only open on supported sites" is off), and Settings lists each optional bank as allowed or not, with Allow / Remove access. **Unverified in a real browser**: the prompt from a popup, and `activeTab` giving the popup the URL.

**Other**: ignore list (`ignored`, capped at 2000 signatures); toolbar badge = number of new rows (set while the panel is open); first install opens Settings (getting-started card until a token is saved); `commands._execute_action` shortcut fires the same `onClicked`; balance = `balance.currentBalance` of the selected account. Bank description goes in `note` (255 max); `counterParty` (Wallet's payer/payee) is set only when the scanner finds a `payee` on the row (CIMB DuitNow). Dates are Malaysia time (UTC+8); records are created at 12:00 +08:00. Old `[m2u:<hash>]` note tags are stripped when reading.

**Settings** (`chrome.storage.local`; defaults in `getSettings`): `onlySupported`, `hideWhenAway` (service worker), `autoRead`, `collectPages` (panel), plus `token`, `accountId`/`accountName`, `currency`, `accountMap`, `transferRules`, `categoryMemory`, `ignored`, `accountList`, `whatsNewFrom` (see What's new). Changes apply live through `storage.onChanged`. The Chrome semantics of "panel stays open across tabs" (global enabled + per-tab enabled with the same path) are inferred from the docs and **untested in a real browser**.

**Busy state** (`setBusy` in `popup.js`): every action that talks to Wallet (read, Replace, Add, Undo, Compare, leaving demo, the first account load) shows an M3 indeterminate progress bar; user-started ones also make `#app` `inert` (dimmed, no clicks or focus, so no double requests) and give the pressed button a spinner and a label ("Replacing…", "Adding…", "Undoing…"). Automatic refreshes show only the bar. A read requested while busy is queued in `rerun` and runs when the work finishes (newest wins, `force` sticks), never dropped. New async actions must go through `setBusy`. The test stub's `env.delay` slows the fake Wallet's writes so tests can see this state. **Exception, the record edits** (Merge/Replace note, Fix in Wallet, Use bank date, and their bulk buttons): they do not lock. `queueEdits` records each transaction in `editingSigs` by **signature**, not row object, because a page read can rebuild the rows at any moment, even between a click and the request (`pendingOf`; `withEditState` shows only a spinner button on such a row and disables its controls; the can* checks skip it). Each queued edit also keeps whether it was a demo edit, so switching demo on or off meanwhile never sends a demo edit or fakes a real one; the result is applied to `currentRow` (the row now on screen with that signature and Wallet record). `editingSigs` counts per signature (identical bank rows share one). If a result has no row to land on, or lands while a read is running (its records may predate the edit), `drainEdits` queues a quiet forced re-read. `drainEdits` runs in try/finally so nothing stays "working" and reads are never held back; an edit's `patch` is worked out when clicked and `apply(row, patch)` reuses it. The queue's messages give way: if an Add or a read changed the status meanwhile, only failures overwrite it and `drainEdits` sends what gathered within 150 ms, up to 10 per PATCH, one request at a time, applying each result to its row (a failure is shown on the row as `editError`). The progress bar shows while `busy || editing`; a page read waits for both (it would rebuild the rows mid-edit). Add, Undo and the rest still lock.

**Demo mode** never reads or writes real settings: its ignores and category choices are in memory only. It swaps in fake accounts, so it must always be leavable: a banner ("Exit demo"), the Demo button (which toggles) and the Read button all call `exitDemo`/`leaveDemo`, which restore the real accounts, clear the list and re-read the page.

## The real Maybank2u page (learned from screenshots)
- History table columns: Date, Description, Amount (no Balance column on the credit card view). Foreign-currency rows show a second line in the description cell.
- Debits show as red "- RM 1,234.56" but the minus is not in the cell text. The owner's account is a credit card, so its Wallet balance is negative. Card repayments appear as "SPAYLATER REPAYMENT…" rows.
- If a layout, sign or account problem appears on the real page, do not ask for real transaction data. Ask them to click **Compare**: it ends with how the page marks amounts (markup, colour, pseudo-element content) with every digit masked, plus the detected account label.

## The real CIMB Clicks page (learned from its HTML)
- `https://www.cimbclicks.com.my/clicks` (an Angular app). History is `table#basicTableHistory` with headers Date, Transaction Details, Money In, Money Out, Balance; newest first; dates like "07 Oct 2026".
- Each Transaction Details cell has a visible block of `<p>` lines (type, reference number, payee, purpose) and a hidden duplicate (`showMoreDetails_N`, `display:none`). `describe()` in `scanner.js` reads the visible lines once, drops number-only lines and joins with " · ". On a DuitNow row (type, account number, name, purpose) the name, the line after the account number, is returned as `payee` instead, left out of `desc` and sent as `counterParty`, so `desc` is "DUITNOW TO ACCOUNT · Netflix"; `signature` includes it. `merchantKey` then uses the most specific later line, because the first is only the transaction type ("DUITNOW TO ACCOUNT", "TR IBG").
- Amounts are `<number-cmp>` spans ("MYR", whole, ".", decimals); every amount has class `positive-number`, so the sign comes only from the Money In / Money Out column (and the Balance check). An empty cell is `&nbsp;`.
- No pagination: rows are appended as you scroll, which the in-page watcher picks up, so the list grows; "Collect across pages" isn't needed.
- On narrow windows (the side panel open) CIMB can switch to a mobile list and hide the table; the scanner reads the hidden table anyway (`describe` uses computed styles, not innerText). The mobile list itself is not read.
- Account detection on CIMB is unverified.

## Wallet API notes
- Spec: `curl -sL https://rest.budgetbakers.com/wallet/openapi`. Read it instead of guessing field names. Paths are under `/wallet/v1/api`.
- Premium only. 300 requests/hour. 409 = first data sync still running. 401/403 = bad token.
- Amount sign decides income vs expense (a transfer is a separate `transfer` field, not a third type). List responses use keys like `records`, `accounts`, `recordRules`; pagination via `nextOffset`. Account has `archived`. `POST /records` max 50 (we send 20), `PATCH` max 10, `DELETE` max 10 ids. Record `recordState` includes `void`.

## Conventions
- Small functions, short comments that explain why.
- Synthetic data (see `CONVENTIONS.md`) means `demo.js` and test fixtures here: no real transactions. The owner's Wallet token only ever lives in extension storage.
- Files use CRLF on disk. Patching with scripts: normalise `\r\n` first and write back the original style, or use the Edit tool. The Write/Edit tools need the file read in the session first.
- `PRIVACY.md` and `store/LISTING.md` must stay in step with behaviour (see `CONVENTIONS.md`).
- New runtime file? Add it to `FILES` in `tools/build.cjs` (the build fails if a shipped file refers to one that isn't listed, and a test checks the zip).

## Testing
`npm test` runs, in `tests/`: `logic` (pure functions), `scanner` (signs and account detection on synthetic tables), `background` (panel rules per setting, shortcut, first run), `panel` (the side panel end to end), `pages` (Settings and the unsupported popup), `build` (the zip). `helpers.mjs` provides `newPanel(browser, server, env, file)`: it serves the repo over HTTP, injects a stub `window.chrome` and a fake Wallet `fetch` driven by `env` (tab URL, rows, detected bank, accounts, records, rules, categories, response headers), and exposes `window.__t` (call logs: created/deleted/patched records, badge text, scans) and `window.__fire(name, …)` to trigger `message`/`updated`/`activated`/`storage` listeners. A missing stub makes `popup.js` throw at load and the panel renders blank, so when adding a new `chrome.*` call to the panel, add it to the stub too.

Not coverable headless, so verify in a real browser when touching them: the service worker and side-panel enable/disable, the in-page watcher on real pagination, `detectAccount` on the real page, and the live Wallet calls for transfers, delete and categories.

**Real browser through MCP** (`.mcp.json`): Google's `chrome-devtools` server, pinned to a version, with a throwaway profile (`--isolated`: no logins, no Wallet token) and telemetry off. It launches `CHROME_PATH`, else Brave. It can `install_extension` (absolute path of this folder), `reload_extension` after edits, open `chrome-extension://<id>/popup.html` or `options.html` as a tab, read console messages, see the service worker, click, type and take screenshots. It cannot open the real side panel (Chrome needs a user click), so check the panel as a tab. The bank sites and `*.budgetbakers.com` are blocked with `--blockedUrlPattern`, so test with **Demo data** or a local synthetic page like the tests use. Do not remove those blocks, and keep this config even where a skill suggests a plainer one (`@latest`, no blocks). To upgrade the server, change the pinned version on purpose after reading its changelog. The owner also has Google's `chrome-devtools` and `a11y-debugging` skills in `~/.claude/skills` (copied from the same release; `SOURCE.txt` says which); update them with the server.

## Releasing to the Web Store
1. Bump `version` in `manifest.json` (the store rejects a re-upload with the same version).
2. `npm test`, then `npm run build -- --clean`: `tools/build.cjs` writes and verifies the zip (the kit's packaging rules apply; the 0.1.0/0.1.1 zips were tar archives).
3. The changelog entry (kit step 2) goes at the top of `CHANGELOG` in `changelog.js`; a test checks the order and that no entry is newer than `manifest.json`.
4. Update `store/LISTING.md` and `PRIVACY.md` if permissions or behaviour changed (the store's data-usage answers must match). `npm run screenshots` after visible UI changes.
5. Upload `dist/bank-to-wallet-sync-<version>.zip`.
