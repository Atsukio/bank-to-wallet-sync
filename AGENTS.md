# AGENTS.md

Chrome/Edge (Manifest V3) extension: reads the transaction table on a supported bank page (Maybank2u and CIMB Clicks) and adds new rows to BudgetBakers Wallet through its REST API. Built for the owner's own use and friends; others are welcome to use it. Repo: https://github.com/Atsukio/bank-to-wallet-sync (branch `main`).

**Shared rules first:** this file covers only what is specific to this extension. The rules common to all of the owner's extensions (design, permissions, privacy, releases, commit messages, Windows gotchas, working with the owner) are in `../extension-kit/CONVENTIONS.md` (imported by `CLAUDE.md`). Where the two differ, this file wins.

## Layout
Plain ES modules, no bundler, **no runtime dependencies**, no build step: load the folder unpacked at `chrome://extensions`. `package.json` exists only for tests and release tooling (`"type": "module"`).

| File | Role |
| --- | --- |
| `manifest.json` | MV3. Side panel is `popup.html`. Service worker is a module. Host permissions: `*.maybank2u.com.my`, `*.cimbclicks.com.my`, `rest.budgetbakers.com`. `commands._execute_action` = Alt+Shift+W. |
| `background.js` | Service worker. Per-tab side panel enable/disable and the "not supported" popup, driven by the `onlySupported` and `hideWhenAway` settings. Icon click and the shortcut call `sidePanel.open`. First install opens Settings. `openPanelOnActionClick` is deliberately `false`. |
| `sites.js` | `SUPPORTED_BANKS` (Maybank2u, CIMB Clicks: name, country, host, URL pattern) and `isSupportedUrl`. The one place to add a bank (plus its host in `manifest.json`). Used by the worker, the panel and Settings. |
| `popup.html` / `popup.js` | The side panel: account picker, reading, review list, add, undo. The biggest file; read its section comments first. |
| `matching.js` | Pure helpers: `signature`, `matchRecords` (pairing bank rows with Wallet records), `carryOver` (keeps manual choices across refreshes), `matchTransferRule`. |
| `wallet.js` | Wallet API client and the pure category logic (`matchRule`, `categoryHistory`, `guessCategory`, `memoryKey`), settings defaults (`getSettings`, `BEHAVIOUR_DEFAULTS`), payload builders, create/update/delete. |
| `scanner.js` | `scanPage`, `detectAccount`, `diagnosePage`, `watchPage` are **injected into the bank page** via `chrome.scripting.executeScript` (all frames). They must stay self-contained (no imports, no outer-scope references). |
| `changelog.js` | `CHANGELOG` (user-facing changes per version, newest first: `{ version, items }`), `compareVersions`, `changesSince`. |
| `whatsnew.js` | The "What's new" card and the NEW badge (see How things work). |
| `demo.js` | Synthetic transactions, accounts, categories, rules, history and transfer rule for the **Demo data** button. |
| `options.html` / `options.js` | Settings: token, default account, currency, four switches, transfer-rule editor, remembered-choice counters, getting-started card, supported banks. |
| `unsupported.html` / `.js` | Popup shown when the icon is clicked where the panel is not allowed; has a cog to Settings (extension pages allow no inline scripts, hence the `.js`). |
| `style.css` | Material Design 3 tokens (generated block) and shared components. Used by every page. |
| `fonts/` | Bundled Roboto (variable weight, Latin) with its Apache 2.0 licence and NOTICE. Must stay in the zip. |
| `store/` | Chrome Web Store listing text and images (generated by `npm run screenshots`). |
| `tests/` | `npm test`: logic, scanner, background, panel, pages and build tests. `helpers.mjs` has the browser/Wallet stub. |
| `tools/` | `build.cjs` (zip), `palette.cjs` (M3 colours), `screenshots.mjs` (store images). |
| `.github/workflows/ci.yml` | Runs `npm test` and `npm run build` on every push and PR. |
| `PRIVACY.md` | Privacy policy (its URL goes in the Web Store dashboard). Keep it true to what the code does. |
| `dist/` | Built upload zip (the one place `.zip` is not gitignored). |
| `CLAUDE.md` | Imports `../extension-kit/CONVENTIONS.md` and this file. Not shipped. |

## Commands
```
npm install            # tooling only
npm test               # everything below; `npm test -- panel` runs files whose name contains "panel"
npm run build          # dist/bank-to-wallet-sync-<manifest version>.zip, verified (add -- --clean to drop older zips)
npm run screenshots    # store/*.png from the demo data
npm run palette -- "#1a73e8" --write
```
Browser for tests: Edge/Chrome are found automatically on Windows, macOS and Linux; set `CHROME_PATH` otherwise. Chrome 137+ ignores `--load-extension`, so tests run the real pages over HTTP against a stubbed `chrome` (see Testing).

## Design system (Material Design 3)
- Colours are M3 roles in the generated block of `style.css`, from `tools/palette.cjs`. Current scheme: **Vibrant, seed `#1a73e8`**. The owner found the earlier muted teal dull. Pages use `--md-*` tokens. `--credit` (income green) and `--warn` (amber) are generated too. The extension icon is still the original teal pixel art.
- Where colour is used: primary for the title, links and filled buttons; secondary for dates and the balance; tertiary for categories and transfers (a transfer row's amount uses `.amt.xfer`, tertiary, since it is neither spending nor income); error for debits and sign/type warnings; chips: `.chip.in` (secondary container) "In Wallet", `.chip.likely` (tertiary container) "Likely in Wallet" and "Transfer", `.chip.check` (error container) "Type differs".
- Typography: M3 type scale in bundled Roboto (variable weight). Base body-large 16/24 +0.5; body-medium 14/20 for secondary lines; label-large 14/20 500 for buttons; label-medium 12/20 500 for chips; title-large 22/28 for headings; headline-medium 28/36 for the Settings title. The owner found a 14px base too small: do not shrink it again.
- Components: pill buttons (outlined; `.primary` filled; `button.text` borderless; `button.icon-btn` round), 4px outlined text fields, compact M3 switches (40x24; the owner found 52x32 too big), collapsible `<details>` descriptions beside each switch, M3 two-line list items in the review list, an M3 divider in the unsupported popup.
- Check every UI change in light and dark. `npm run screenshots` renders the real pages.

## How things work

**Reading the page** (`popup.js` `readPage`)
- Auto-read: the panel reads the active supported tab when it opens and re-reads (debounced 100 ms) on a `b2w-page-changed` message, `tabs.onUpdated` for the active tab and `tabs.onActivated`. `watchPage()` (MutationObserver, 250 ms debounce, ping only) is injected on every read because the site changes its table without navigating. Chrome cannot open a side panel without a click, so the panel never opens by itself.
- `auto` reads are gated by the `autoRead` setting and skip when `busy`, in demo mode or without a token; `quiet` reads refresh in place (after an account change, ignore, undo); `force` re-checks Wallet even if the bank rows are unchanged. Switching back to a tab or focusing the panel forces a Wallet check. Manual button reads always run.
- `carryOver` keeps what the user did by hand (ticks, flipped signs, transfer choice, manual category) across re-reads, keyed by `signature` (date|desc|amount as read).
- `collectPages`: rows from earlier pages are merged into the list until **Clear list**.

**Amount signs** (`scanner.js`): a wrong sign adds an expense as income, so it is checked three ways.
1. `parseAmount` reads the cell text (leading/trailing minus incl. Unicode minus, brackets, DR/DB/DEBIT).
2. If the text has no sign, `visualSign` reads the cell's CSS: a minus drawn by `::before`/`::after`, or red/green text. Maybank2u draws debits in red with the minus in CSS, so text alone read them as positive.
3. `reconcileSigns` overrides using the Balance column when there is one (balance movement between neighbouring rows is the truth). Rows it can't verify are flagged `unsure` only if the text proved wrong elsewhere on the page; the panel leaves them unticked with a Flip sign button.

**Which Wallet account** (`popup.js` accounts section)
- `detectAccount()` (best-effort, **never verified on the real page**) returns `{label, digits}` from headings, an account drop-down or account/card-classed elements. `bankKey` = `d:<last4>` else `l:<normalised label>`. `settings.accountMap[key]` maps it to a Wallet account; else the default `settings.accountId`; else the panel asks (`resolveAccount`, Add disabled). Choosing in the picker saves the mapping (or the default if no bank account was detected). The detected label is shown under the picker so it can be checked, and **Compare** prints it (digits masked).
- Accounts come from `listAccounts` (active only), cached 10 min and stored as `accountList` for Settings.

**Matching against Wallet** (`matching.js` `matchRecords`)
- Nothing is written to Wallet to track syncs. Existing records for the date range are paired one-to-one, three passes: exact description + same type → done; same type → likely; **opposite type → likely with `typeMismatch`** (shown as "Type differs", no Replace, so a wrongly signed record isn't hidden as "In Wallet"). **Fix in Wallet** (`fixType`, bulk `#fixAll` when 2+) PATCHes only `amount: { value: <bank signed amount> }`, which also sets the type; not offered when the Wallet record is a transfer (`existingRecords` marks `transfer`), since flipping one side breaks the pair. Ignored rows take no part. `sameDescription(walletText, bankDesc)` is directional: it ignores case/punctuation and accepts an 8+ char truncated prefix either way, or a Wallet note that contains the whole bank description (8+ chars) anywhere, because people add details to notes. Records with `recordState: void` are ignored.
- Likely rows show the Wallet note and offer **Merge notes** (`mergedNote`: "<wallet note> · <bank description>", the user's part shortened with "…" to fit 255, never the bank's) and **Replace note** (note = bank description); each button's tooltip shows the resulting note; plus bulk `#mergeAll` / `#replaceAll`. Both PATCH only `note`. `sameDescription` also treats any " · " part of a Wallet note equal to the bank description as a match, so merged notes match even when the description is shorter than 8 characters. `existingRecords` keeps the record's own `note` separately from its other texts for this.
- A fourth pass catches records on a nearby date: same amount and type, Wallet dated up to `MAX_DATE_LAG` (3) days before (logged before the bank posted it) or after (an automated/scheduled Wallet record) the bank row; closest day first, the earlier side wins a tie, same description preferred, run last so a real bank row on that other day keeps its record. Sets `t.dateLag` = bank date minus Wallet date (negative when Wallet is later); the row offers **Use bank date** (`moveDate`: PATCH `recordDate` shifted by the lag, so the time of day is kept; bulk `#moveAll`), and Merge/Replace only after that. `analyse` fetches records from `shiftDate(earliest, -MAX_DATE_LAG)` to `shiftDate(latest, +MAX_DATE_LAG)`; `showCoverage` counts only the bank's dates.
- The REST API serves its own synced copy of Wallet, so a record deleted in the app can keep showing for a while. `existingRecords` captures `X-Sync-In-Progress` and `X-Last-Data-Change-At`; the coverage line shows them. **Compare** lists each Wallet record's source, state and updatedAt.

**Categories** (a record with none shows as "Unknown expense")
- Order: remembered manual choice (`categoryMemory`, keyed by `memoryKey`) → Wallet rule (`GET /record-rules`, `matchRule`: substring, longest keyword, skips transfer rules and other accounts' rules) → `guessCategory` from `categoryHistory` (last ~6 months, any account, up to 1000 records; same description, else same merchant; same income/expense type; "Unknown" ignored; most common wins). The per-row **Change** picker uses `listCategories` (`GET /categories`, response key assumed to be `categories`, **unverified live**).
- Caches: rules 5 min, history 10 min, categories 30 min, accounts 10 min. Failures never block adding.

**Transfers** (`transferRules` in Settings, or "Make transfer" per row): the record is created with `transfer: { pairingMode: 'new', accountId }` (no category/labels); Wallet creates the mirror record, whose id comes back as `createdMirrorRecordId`. The other account's page then sees the mirror as "In Wallet". **Unverified live.**

**Undo**: after an add, `lastAdd = { groups: [[id, mirrorId?]], at }` is saved (15 min). Undo calls `DELETE /records` with `{ ids }` (max 10 per request; a transfer and its mirror must go in the same request, hence `chunkGroups`). **Unverified live**; demo mode pretends.

**Balance check** (`readBalance` in `scanner.js`, `renderReconcile` in `popup.js`): reads the page's "Outstanding Balance", else "Current/Ledger", else "Available", else "Statement" (and Malay labels), the amount right after its label, up to 5 levels up (CIMB: `.value-box > label + .value number-cmp`; Maybank2u card: `<p>` label in `.panel-body`, amount in the sibling `.well`). Outstanding beats statement because a card's statement balance is only what was owed on the statement date (the owner asked for this). Compared with the Wallet account's balance; a card/loan (`accountType` CreditCard/Loan/Mortgage, or an "outstanding"/"statement" label) counts the bank figure as owed (negative); on such an account an "Available" figure is the credit left, so the check is hidden. **Adjust** asks first (warning if new rows aren't added yet, since they'd be counted twice), then POSTs one record for the difference: note "Balance adjustment to match the bank's …", `recordState: 'reconciled'`, dated now, no category (the API has no adjustment concept). It goes into `lastAdd`, so Undo removes it. `detectAccount` first uses `option[data-account-no]` (CIMB tags its account picker with `data-label` / `data-account-no`).

**What's new** (`whatsnew.js`, `changelog.js`): Chrome updates extensions silently. `onInstalled` with reason `update` and a different `previousVersion` (an unpacked reload reports the same version) stores `whatsNewFrom: <previousVersion>` (keeping an older one already stored, so two updates in a row show both) and sets a global NEW badge in the primary colour (hex mirrored in `whatsnew.js`, since the worker has no CSS); `onStartup` re-sets it while `whatsNewFrom` is stored, because badge text doesn't survive a restart. The side panel and the "not supported" popup both show the card (the badge is on every tab), listing `changesSince(whatsNewFrom, running version)`: one version is titled "What's new in X.Y.Z", several get a heading each, newest first. Built with `textContent`. "Got it" removes `whatsNewFrom` and clears the global badge; no matching entries clears them silently (a quiet release). The panel's own per-tab row count badge overrides NEW on that tab only. No tab is opened and no permission is needed. Preview: in the service worker console, `chrome.storage.local.set({ whatsNewFrom: '0.2.0' })`, then open the panel.

**Other**: ignore list (`ignored`, capped at 2000 signatures); toolbar badge = number of new rows (set while the panel is open); first install opens Settings (getting-started card until a token is saved); `commands._execute_action` shortcut fires the same `onClicked`; balance = `balance.currentBalance` of the selected account. Bank description goes in `note` (255 max), `counterParty` is unset. Dates are Malaysia time (UTC+8); records are created at 12:00 +08:00. Old `[m2u:<hash>]` note tags are stripped when reading.

**Settings** (`chrome.storage.local`; defaults in `getSettings`): `onlySupported`, `hideWhenAway` (service worker), `autoRead`, `collectPages` (panel), plus `token`, `accountId`/`accountName`, `currency`, `accountMap`, `transferRules`, `categoryMemory`, `ignored`, `lastAdd`, `accountList`, `whatsNewFrom` (see What's new). Changes apply live through `storage.onChanged`. The Chrome semantics of "panel stays open across tabs" (global enabled + per-tab enabled with the same path) are inferred from the docs and **untested in a real browser**.

**Busy state** (`setBusy` in `popup.js`): every action that talks to Wallet (read, Replace, Add, Undo, Compare, leaving demo, the first account load) shows an M3 indeterminate progress bar; user-started ones also make `#app` `inert` (dimmed, no clicks or focus, so no double requests) and give the pressed button a spinner and a label ("Replacing…", "Adding…", "Undoing…"). Automatic refreshes show only the bar. A read requested while busy is queued in `rerun` and runs when the work finishes (newest wins, `force` sticks), never dropped. New async actions must go through `setBusy`. The test stub's `env.delay` slows the fake Wallet's writes so tests can see this state.

**Demo mode** never reads or writes real settings: its ignores and category choices are in memory only. It swaps in fake accounts, so it must always be leavable: a banner ("Exit demo"), the Demo button (which toggles) and the Read button all call `exitDemo`/`leaveDemo`, which restore the real accounts, clear the list and re-read the page.

## The real Maybank2u page (learned from screenshots)
- History table columns: Date, Description, Amount (no Balance column on the credit card view). Foreign-currency rows show a second line in the description cell.
- Debits show as red "- RM 1,234.56" but the minus is not in the cell text. The owner's account is a credit card, so its Wallet balance is negative. Card repayments appear as "SPAYLATER REPAYMENT…" rows.
- If a layout, sign or account problem appears on the real page, do not ask for real transaction data. Ask them to click **Compare**: it ends with how the page marks amounts (markup, colour, pseudo-element content) with every digit masked, plus the detected account label.

## The real CIMB Clicks page (learned from its HTML)
- `https://www.cimbclicks.com.my/clicks` (an Angular app). History is `table#basicTableHistory` with headers Date, Transaction Details, Money In, Money Out, Balance; newest first; dates like "07 Oct 2026".
- Each Transaction Details cell has a visible block of `<p>` lines (type, reference number, payee, purpose) and a hidden duplicate (`showMoreDetails_N`, `display:none`). `describe()` in `scanner.js` reads the visible lines once, drops number-only lines and joins with " · ". `merchantKey` then uses the most specific later line, because the first is only the transaction type ("DUITNOW TO ACCOUNT", "TR IBG").
- Amounts are `<number-cmp>` spans ("MYR", whole, ".", decimals); every amount has class `positive-number`, so the sign comes only from the Money In / Money Out column (and the Balance check). An empty cell is `&nbsp;`.
- No pagination: rows are appended as you scroll, which the in-page watcher picks up, so the list grows; "Collect across pages" isn't needed.
- On narrow windows (the side panel open) CIMB can switch to a mobile list and hide the table; the scanner reads the hidden table anyway (`describe` uses computed styles, not innerText). The mobile list itself is not read.
- Account detection on CIMB is unverified.

## Wallet API notes
- Spec: `curl -sL https://rest.budgetbakers.com/wallet/openapi`. Read it instead of guessing field names. Paths are under `/wallet/v1/api`.
- Premium only. 300 requests/hour. 409 = first data sync still running. 401/403 = bad token.
- Amount sign decides income vs expense (a transfer is a separate `transfer` field, not a third type). List responses use keys like `records`, `accounts`, `recordRules`; pagination via `nextOffset`. Account has `archived`. `POST /records` max 50 (we send 20), `PATCH` max 10, `DELETE` max 10 ids. Record `recordState` includes `void`.

## Conventions
- Small functions, short comments that explain why.
- Synthetic data (see `CONVENTIONS.md`) means `demo.js` and test fixtures here: no real transactions. The owner's Wallet token only ever lives in extension storage.
- Files use CRLF on disk. Patching with scripts: normalise `\r\n` first and write back the original style, or use the Edit tool. The Write/Edit tools need the file read in the session first.
- `PRIVACY.md` and `store/LISTING.md` must stay in step with behaviour (see `CONVENTIONS.md`).
- New runtime file? Add it to `FILES` in `tools/build.cjs` (the build fails if a shipped file refers to one that isn't listed, and a test checks the zip).

## Testing
`npm test` runs, in `tests/`: `logic` (pure functions), `scanner` (signs and account detection on synthetic tables), `background` (panel rules per setting, shortcut, first run), `panel` (the side panel end to end), `pages` (Settings and the unsupported popup), `build` (the zip). `helpers.mjs` provides `newPanel(browser, server, env, file)`: it serves the repo over HTTP, injects a stub `window.chrome` and a fake Wallet `fetch` driven by `env` (tab URL, rows, detected bank, accounts, records, rules, categories, response headers), and exposes `window.__t` (call logs: created/deleted/patched records, badge text, scans) and `window.__fire(name, …)` to trigger `message`/`updated`/`activated`/`storage` listeners. A missing stub makes `popup.js` throw at load and the panel renders blank, so when adding a new `chrome.*` call to the panel, add it to the stub too.

Not coverable headless, so verify in a real browser when touching them: the service worker and side-panel enable/disable, the in-page watcher on real pagination, `detectAccount` on the real page, and the live Wallet calls for transfers, delete and categories.

## Releasing to the Web Store
1. Bump `version` in `manifest.json` (the store rejects a re-upload with the same version).
2. `npm test`, then `npm run build -- --clean`. The zip is written and verified by `tools/build.cjs`. **Do not build zips with `tar`**: Git for Windows' GNU `tar -a -cf x.zip` silently writes a plain tar archive, which the store rejects (the committed 0.1.0 and 0.1.1 zips were affected).
3. If users should hear about the release, add its entry at the top of `CHANGELOG` in `changelog.js` **in the same commit as the version bump**: plain sentences about what they'll notice, no internals (a test checks the order and that no entry is newer than `manifest.json`). A release without an entry updates quietly.
4. Update `store/LISTING.md` and `PRIVACY.md` if permissions or behaviour changed (the store's data-usage answers must match). `npm run screenshots` after visible UI changes.
5. Upload `dist/bank-to-wallet-sync-<version>.zip`.
